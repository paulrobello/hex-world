# Stages

Run every command from the repo root. Each stage must pass before the next one starts.

1. **Reference.** `make refs PIECE=<id>`. Generates Higgsfield reference images into `assets-source/refs/<id>/` with `refs.json`. Stop here until the owner has reviewed the images and `assets-source/refs/<id>/approval.json` exists. No modeling before approval (R2).
2. **Build.** `make kit-build PIECE=<id>` runs `scripts/blender/kit/<id>.py` headless and writes `target/kit-stage/<id>/{<id>.glb,<id>.<channel>.png,bake-report.json,export-report.json}`. This covers high-poly, LOD0 + UVs, bake, LODs + collider, sockets and export. A tileable set is `make kit-material SET=<set>` (generator `scripts/blender/kit/mat_<set>.py`), which also compresses it.
3. **Compress.** `make kit-compress PIECE=<id>`. Meshopt GLB, UASTC source transcoded to BC7 and ASTC KTX2, PNG fallback, per-class byte budgets (`CLASS=hero` or `export-report.json` `budgetClass`; see `project.md`) and `compress-report.json`. Output is written atomically, so a budget failure leaves `assets/kit/p1/<id>/` untouched.
4. **Renders.** `make kit-renders PIECE=<id>`. The Blender socket round-trip check on `target/kit-stage/<id>/`, then the 6-view render into `assets-source/kit/<id>/renders/`, as evidence only (Blender's view transform does not match Bevy's tonemapper). Renders carry no date metadata, so an unchanged GLB re-renders byte-identically.
5. **Provenance.** First add the piece to `assets/kit/manifest.json`: the assembler refuses to stamp `validation.pass` for a piece the gate cannot see. Then `make kit-provenance PIECE=<id> REFS=assets-source/refs/<ref-id>` checks the inputs without writing, runs the gate without the provenance tests, runs the renders, and only then writes `assets-source/kit/<id>/provenance.json` (`provenance.md`) with `validation.pass = true`, so a failed run leaves the committed record untouched. It refuses up front when `target/kit-stage/<id>/` lacks the GLB or `export-report.json` (the renders re-import them): run `make kit-build PIECE=<id>` first. `REFS=` is required for real pieces: it carries the owner's reference approval. The assembler refuses when the generator or a helper changed since the build: rebuild first. Sets use `make kit-material-provenance SET=<set>`.
6. **Gate.** `make kit-check`. The Rust reimport gate over every piece in `assets/kit/manifest.json` and the committed fixture (`gates.md`). CI runs it through `make test`, so it reads committed files only.
7. **In-engine shot.** `make shots-kit` (native) and `make web-shots-kit` (browser), plus the review sheet views (SKILL.md, "Owner checkpoints"). The in-engine screenshots the owner reviews. Owner approval is recorded by the controller. The kit scenario compiles `assets/kit/manifest.json` in (`include_str!`) and lays pieces out in `kit_scene::kit_layout`, so add the manifest entry and the layout placement before building the app for the shot. For a one-off camera, run your own script: `cargo run -p hex-app --release -- --script <file.json> --size 1600x1000 --seed 1 --fps off --tilt off [--kit_hooks night]`, in the `scripts/shots/kit.json` format. The release binary is `target/release/hex-world` (package `hex-app`), not `hex-app`.

**After approval, the generator and its `_*.py` helpers are frozen.** The gate re-hashes them on every run, so even a comment edit fails `make kit-check` until the piece is rebuilt, re-compressed, re-provenanced and re-approved. Put shared changes in `scripts/blender/lib/` (outside provenance, covered by `make blender-test`) or wait for the piece's next rebuild.

## Interactive route

For hero pieces authored in the owner's live Blender (the hero oak `tree_hero_oak` is the worked example). Only the high-poly is interactive. Everything from LOD0 on is the scripted pipeline above.

1. **References.** `cat assets-source/refs/<id>/approval.json`. Stop unless the owner approved them (R2).
2. **Connect.** The owner runs Blender 5.2 with the uvx `blender-mcp` add-on on TCP 127.0.0.1:9876. Drive it with `python3 scripts/blender/mcp_live.py info` (scene info) or `python3 scripts/blender/mcp_live.py exec <file.py>` (stdlib client, one JSON request per connection, `{"type":"execute_code","params":{"code":...}}`, 600 s timeout, exit 1 on an error status). Keep each step as a committed file under `assets-source/kit/<id>/live/NN_*.py` so the session is replayable. `exec` prepends `REPO = "<checkout root>"`: steps build every path from `REPO` and never hard-code a host or worktree path (`test_mcp_live` checks the committed steps). The desktop app's `mcp__Blender__*` connector is a different add-on and timed out here, so do not depend on it. If 9876 does not answer (`lsof -nP -iTCP:9876 -sTCP:LISTEN`), ask the owner to start Blender with the add-on, then retry. Never substitute headless authoring without the owner's say-so.
3. **Ground and protect the owner's data.** Read `bpy.data.filepath`, the scenes and the material count first. Work only in a scene named `<id>`, with every datablock prefixed `<id>`. `bpy.data.images.load` names an image after its file, so rename every loaded image (textures, the HDRI) to the prefix right after loading. Never modify, rename or delete the owner's objects, and never save over the owner's open file.
4. **Author and show.** Put shared geometry and materials in an importable helper (`scripts/blender/kit/_<family>.py`) that both the live steps and the export stage use, so LOD receivers come from the same skeleton. Set the scene to `BLENDER_EEVEE`, the viewport to Rendered shading through the piece camera, and light it with prefixed key, fill and rim lights plus the look-dev HDRI world (`make fetch-hdri` puts it in `assets-source/hdri/`). Self-review by rendering stills to `target/` and reading them against the approved reference. Showcase lights, camera and ground stay out of the bake inputs and the export root (the export stage deletes every object except the `*_high` meshes).
5. **Save to the blend store.** `bpy.data.libraries.write(path, {scene}, path_remap="ABSOLUTE")` writes a copy of only the piece scene to `paths.blend_path(<id>)` in the main checkout (`project.md`, "The blend store"). Assert that `bpy.data.filepath` and the owner's scenes are unchanged before and after. Record the SHA-256 (`shasum -a 256`).
6. **Export stage.** `scripts/blender/kit/<id>.py` opens that `.blend` (default `paths.blend_path`, override `HEXW_BLEND`) and runs the scripted LOD0, UV, bake, LOD, collider and export steps. Bakes stay headless on Cycles. The bake report records the `.blend` SHA-256 as `blend.sha256`.
7. **Gates.** `make kit-build`, `make kit-compress`, `make kit-determinism PIECE=<id>` (the GLB is byte-identical across two runs), add the piece to the manifest, then `make kit-provenance PIECE=<id> ROUTE=interactive REFS=assets-source/refs/<id>` (BLEND defaults to the store; the target fails when the `.blend` does not resolve) and `make kit-check`. Provenance carries `route: "interactive"`, `blendRef` and the export stage's `generator` and `generatorDeps` hashes. The gate fails an interactive piece without a store-relative `blendRef`, or whose `blendRef.sha256` differs from the bake report's `blend.sha256`.
**Headless replay of an interactive piece.** When the owner asks for a polish without the live session, rebuild the high poly with a step that opens the stored `.blend` headless (`"$BLENDER" -b <store blend> --factory-startup --python-exit-code 1 -P assets-source/kit/<id>/live/NN_*.py`), never `mcp_live.py`. Such a step takes the checkout root as `globals().get("REPO")` or from `__file__` (`test_mcp_live` forbids a `REPO =` line), touches only the piece's prefixed objects, writes the new revision through `paths.blend_path` with `bpy.data.libraries.write`, and first copies the replaced revision aside in the store as `<id>_high.<sha12>.blend`. The hero oak's `live/06_p2_highpoly.py` is the worked example; an `OAK_BLEND_OUT`-style override lets geometry iterate on a scratch `.blend` (`HEXW_BLEND=…`, `HEXW_SKIP_BAKE=1`) before the store is written.
8. **Shots.** Build first (`make web-shots-kit` rebuilds the wasm). Shots are not timing measurements, so take them without waiting on host load: run them under `caffeinate -d -u`, check each PNG's mean, re-run once if one is black, then build the review sheet (SKILL.md, "Owner checkpoints") for the owner checkpoint. The controller records approval.
