# river_fork_base friction

- **The engine called the fork a spring (0 min lost, found before building).** `water::tiles::water_kind` took any Edge-to-Node River segment on a non-coast tile as a spring, and `river_segments` gave every node end `RiverEnd::Spring`, so a three-arm tile would have drawn the spring's pool and flowed out of all three arms. Fix in the integration patch: a River node shared by two or more segments is a junction (`river_junction`, `RiverEnd::Junction`), the tile stays `WaterKind::River`, and `junction_sources` orients the arms. Proposed skill text (`pitfalls.md`, Water beds): "A new river tile with a node is a spring unless the node joins two or more River segments: check `water::tiles::water_kind` and `river_segments` before modelling a bed for it, since the engine draws its own analytic bed whatever the kit builds."
- **`_river.channel_cap` joins every pair of consecutive rows at equal offsets (2 min).** Three wedges in one row list would have joined arm 0's joint row to arm 2's crease row across the channel (crossing constraints, a Steiner-vertex assertion). An empty row between wedges joins nothing, so `_river.build_base` builds the fork unchanged from `_river.LAYOUTS["fork"]`. Proposed skill text (`lib-contracts.md` or `pitfalls.md`): "`channel_cap` rows may be any polylines whose points carry the profile of their offset key; separate independent strips with an empty row."
- **The play scenario starts with a meadow at (0, 0) (6 min).** The first review script placed the fork at the origin, which was taken, so the fork and two straights were silently refused and only the bend landed. Read `dump_state` `tiles` after a review run before judging the frames. No skill change: `docs/agent-operability.md` already describes the start world; noted here for the next river review script.
